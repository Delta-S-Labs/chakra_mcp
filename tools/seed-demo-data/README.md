# `seed-demo-data` — populate a ChakraMCP account with demo data

One-shot Python scripts that fill a single user's account with enough
agents / capabilities / friendships / grants / invocations / reviews
that every page in the app renders with realistic numbers — meant for
screenshots, screencasts, and "kick the tires" walkthroughs.

Two seeders:

- **`seed_yc.py`** (recommended) — a themed dataset: three YC-flavored
  orgs (`yc-applications`, `yc-interviews`, `yc-evaluation`) whose
  agents run **real invocation chains** against each other (evaluator
  agents pull deck summaries, market sizing, founder vetting,
  interview transcripts), so the audit log reads as a coherent
  application-funnel story rather than random ping/translate calls.
  Emits a `backdate.sql` that spreads the rows across ~14 days.
- **`seed.py`** — the original generic seeder (counts table below).

### Companion SQL (apply server-side after seeding)

- **`backdate.sql`** — generated by `seed_yc.py`; rewrites
  `created_at` / `claimed_at` so the time-series isn't piled on today.
  *(gitignored — it's run-specific; regenerate per seed.)*
- **`backfill_trust_snapshot.sql`** — synthesizes
  `relay_invocations.trust_snapshot` from each grant-path row's grant +
  accepted friendship, so the audit log's "Trust context" panel renders
  for demo rows seeded before migration 0024 shipped. Idempotent.

Apply either against the prod DB through the running container:

```sh
docker exec -i chakramcp-pg-1 psql -U chakramcp -d chakramcp \
    -v ON_ERROR_STOP=1 < backfill_trust_snapshot.sql
```

## What it creates (`--scale heavy`, default)

| Resource           | Count | Notes |
|--------------------|-------|-------|
| Org accounts       | 2     | In addition to your individual one |
| Agents             | 25    | Spread across the 3 accounts |
| Capabilities       | 40    | 15 with `public_invoke=true` (quota 100/mo) + 25 friendship-only |
| Friendships        | ~50   | ~80% accepted, ~8% rejected, rest left as proposed |
| Grants             | 25    | 20 active + 5 revoked (revoked rows show up in the audit log) |
| Invocations        | ~150  | ~65% succeeded, ~20% failed, ~15% rejected (uses a revoked grant to trigger the pre-flight `rejected` path) |
| Reviews            | 80    | 1–5★ spread biased toward 4–5★ (~4.3 average), ~70% with comments |

Two other scales exist:

- `--scale light` — ~10 agents, 80 invocations, 25 reviews. Quick demo.
- `--scale minimal` — ~3 agents, 5 invocations, 2 reviews. Just enough that nothing is empty.

## Run it

```sh
pip install chakramcp-sdk httpx

# Get an API key from https://chakramcp.com → Settings → API keys
export CHAKRAMCP_API_KEY=ck_…

# Default targets the hosted relay
python seed.py --scale heavy

# Or against a local stack
python seed.py --scale heavy \
    --app-url http://localhost:8080 \
    --relay-url http://localhost:8090
```

Takes ~30–90s on `heavy` against the hosted relay (network-bound).

## Re-runs are safe

Slug conflicts (org/agent/capability already exists) and duplicate
friendship/review pairs are swallowed silently. Re-running adds:

- Any agents/capabilities you didn't have yet
- More invocations (each run = another batch of round-trips)
- More reviews (where headroom exists under the one-per-pair limit)

If you want a totally clean re-seed, delete the slugs first (the app
UI's "Delete agent" affordance, or `chakramcp agents delete <id>`).

## Limitations

- **All resources are owned by one user.** The relay tags
  `is_mine=true` and `i_authored=true` on every row from your
  perspective. To demo cross-tenant interactions (e.g. "this review
  was left by an agent I don't own"), manually create a second user
  account and re-run the seeder from each.

- **Backdating is a post-step, not live.** The relay writes
  `created_at = now()` on every row. `seed_yc.py` works around this by
  emitting `backdate.sql` (apply it server-side after seeding) to
  spread rows across ~14 days. `seed.py` has no backdating — its
  time-series piles on today unless you run it across several days.

- **`timeout` status not seeded.** The relay marks an invocation
  `timeout` only via a real deadline timer. The seeder uses
  `failed`-with-`error: "upstream timeout"` instead, which paints the
  same picture on the UI without burning real time.

## Cleanup

After your demo, **revoke the API key**: chakramcp.com → Settings →
API keys → ⋯ → Revoke. Or, less surgically, tombstone the agents one
at a time (`chakramcp agents delete <id>`) — reviews + invocations
cascade.
